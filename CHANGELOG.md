# Changelog

## Unreleased

- Dependency checks: `deny.toml` for `cargo deny check` (advisories, licences, sources) and Dependabot updates.
- Fixed: pressing play could show the playhead at the end although playback ran from the right place. The client kept an outdated clock offset after the server's clock had moved (restart, sleep); it now replaces a contradicting measurement and measures again before play.
- Mixer: “Analyse” is now “Split” and is offered only for a recording without stems; splitting no longer finds the song structure. The new “Create regions” (`POST /api/v1/recordings/{id}/stems/regions`) finds it from the stems and keeps it, so asking again adds missing regions without a new run. The analysis program gained `--structure` and reports finer progress; run `tools/analysis/install.sh` again after updating.
- The library marks recordings that have stems (`has_stems` in the recording list). Removed from the interface: “Analyse again” in the library and deleting stems in the mixer; the endpoints remain.
- The README describes the current features and limits; `SECURITY.md` says how to report a vulnerability and what the server does not protect against.
- Fixed: a stem analysis could stay at 95 % although the program had ended. The server now goes by the end of the program, not the end of its output, and removes left-over temporary stem files at start-up.
- Specification of stems, a mixer view and structure analysis (ADR-015; architecture and design specification section 5.7).
- Stem packages on the server: `POST /api/v1/stem-packages` takes a ZIP with `manifest.json` and audio files and gives the recording with that content hash its stems (kept in `<data_dir>/stems`) and the song sections as regions; the stems of a recording can be listed, shown as waveforms, exported as a package and deleted. The shared state carries their mix (stems on or off; volume, mute and solo per stem), stored with the recording and reset when the stems change; the intents `set_stems_enabled`, `set_stem_volume`, `set_stem_muted` and `set_stem_solo` change it. The engine sums the stems before time stretching and decodes them once a mix first uses them. Stems must have the sample rate of the recording. A mixer view next to the player shows one waveform lane per stem on a common time axis with one playhead, volume, solo and mute per lane, a switch between stems and original, and import, export and delete of the stem package.
- Analysis into stems with an optional external program (`tools/analysis`, found at `<data_dir>/analysis/run` or set with `analysis_program`): started in the mixer, one job at a time with progress; the song sections it finds become regions. The models are not part of Veltrunox; see their terms in `tools/analysis/README.md`.
- macOS application (ADR-014), first state: the interface and the server in one program, usable without a network. A settings dialog switches a server for the network on and off (port, optional HTTPS); browsers then get the web app and sign in as usual. The headless server is unchanged; its wiring is now a library. The application says “Open recordings” where the browser says “Upload”.
- HTTPS (ADR-008): the new setting `tls` is `off` (default, plain HTTP), `local-ca` (the server creates its own certificate authority in `<data_dir>/tls`, issues a certificate for `<hostname>.local` and its local addresses, renews it by itself and offers the authority at `/ca.crt`) or `files` (`tls_cert_file`, `tls_key_file`; read at start). With HTTPS the browser treats the app as a secure context, which lets it use its faster renderer. `veltrunox-mcp` speaks HTTPS and trusts the certificate named in `VELTRUNOX_CA`.
- Waveform: the mouse wheel over the waveform zooms around the pointer (the page does not scroll then; a sideways swipe still pans). A pinch keeps the time under the fingers in place while they move. Less work per zoom step: the peaks are drawn in two calls instead of one per pixel column, ruler labels and the region lane layout are reused.
- Marker list: tick boxes appear only after “Edit” (“Done” leaves it and drops the ticks); the highlighted row is no longer shifted. A region can be duplicated and split at the playhead (row menu and long press in the waveform). Splitting is one server call, `POST /api/v1/regions/{id}/split`.
- Dragging the position of a stopped recording still previews it, also while resting, but the play button keeps showing “stopped” and letting go leaves the position where it was let go, stopped.
- The space bar plays and pauses on the player page unless a text input has the focus.
- Pinching works over the whole timeline (ruler, labels, playhead, regions), also when the first finger already moved.
- Library: the analysis state filters are gone; “Upload recordings” is styled like “Add region”.
- The title bar shows when the web app was built (set by `scripts/build-web.sh`), next to the connection status (not on a phone). Copying an API token in a browser now copies directly on the click.
- Regions in the marker list can be ticked. With two or more ticked, “Combine regions” replaces them by one region over their whole span (earliest start to latest end, gaps included; destructive) and “New region from selection” adds that region, named after the ticked ones (“A + B”), and keeps the originals; both ask for name and times first. Combining is one server call, `POST /api/v1/recordings/{id}/regions/merge` (body: the regions with the versions seen, name, range): in one transaction the listed regions are deleted and one new region (new id, first version) is created; a missing region, one of another recording or a stale version refuses the request and changes nothing. The region being played is highlighted in orange in the list (bar, equaliser icon) and in its lane in the waveform; it is recognised by its start and end matching the shared play range. Ticked regions and the region selected for editing are drawn in the soft teal, so orange means only “playing”.
- Copying a new API token works in a browser on a page served over plain HTTP from a host other than localhost: there the browser has no clipboard API and copying failed; the app now falls back to the legacy copy command.

- Every signed-in account can change its own password: `PUT /api/v1/me/password` (body `current_password`, `new_password`) checks the current password (a wrong one counts as a failed sign-in and is refused with `wrong_current_password`), applies the password rules and ends all sessions of the account, this one too; guests and API tokens are refused, API tokens stay valid. The account menu has “Change password” (not for guests): a dialog with the current password and the new one twice, each with a show/hide toggle, problems named at their field, a notice about the sign-out beforehand and, afterwards, the sign-in screen with a note. The admin's password dialog and the form for a new user ask for the password twice too, and the notice after an admin change says the user is signed out everywhere. Specified in section 9.7 of the design specification (D-27).
- Bookmark ids are never used again: `labels` and `regions` are `AUTOINCREMENT` (migration 7, stored bookmarks keep their ids and versions). Before, a bookmark made after the last one was deleted could get the id of the deleted one, so an id and version in an old export file could name another bookmark and hide a conflict.
- Saving an export in a browser now counts as saved: a browser downloads the file and `file_picker` reports no place, which the app took for a cancelled save, so the notice "Saved" did not appear.
- API tokens in the interface: the account menu of a signed-in account (not of a guest) opens a dialog that lists the person's tokens with reach, creation and last use, makes a token from a name and a reach (“Read only” or “Read and edit bookmarks”) and revokes one after a confirmation that names it. The text of a new token is shown once, with a copy action, and is removed from the screen when hidden or when the dialog closes.
- Bookmark exchange in the interface: an exchange menu in the marker panel (one recording) and in the library (all recordings) exports as JSON or CSV and, with the right to edit bookmarks, imports a file. An import first shows a preview per recording (ready, conflict, invalid, unknown) with the numbers of new, changed, unchanged and removed bookmarks, issues with their place (“Label 3”) in words, and, with conflicts, a choice to overwrite entries changed meanwhile; only “Apply” writes. New refusal codes are worded in German and English (`outside_recording`, `import_malformed`, `csv_invalid`, …). The marker panel wraps its buttons on a narrow screen.
- The client core and the bridge can export and import bookmarks and manage API tokens (`export_bookmarks_text`, `import_bookmarks_text` with `dry_run` and `overwrite`, `list_api_tokens`, `create_api_token`, `revoke_api_token`); the interface follows.

- `veltrunox-mcp`, a program that serves bookmark tools to an LLM over the Model Context Protocol (standard input and output, no server of its own): `list_recordings`, `get_recording`, `get_bookmarks` and `set_bookmarks` (replaces all bookmarks of one recording, with `dry_run`; ids and versions of entries taken over make a concurrent change a conflict). It reaches the server through its HTTP API with an API token (`VELTRUNOX_TOKEN`, address in `VELTRUNOX_URL` or `--url`), so it can do no more than the token. Server refusals come back to the LLM as tool errors with the server's reason. Setup in the README.

- Bookmarks can be replaced and exported as a whole: `PUT /api/v1/recordings/{id}/bookmarks` swaps all labels and regions of a recording in one transaction (new ids, first versions; any invalid entry, or one past the end of a known length, refuses the whole request with `empty_name`, `empty_range` or `outside_recording` and changes nothing), `GET /api/v1/export` and `GET /api/v1/recordings/{id}/export` return recordings with their details and bookmarks (`format_version` 1). Connected clients are told that the bookmarks changed. The interface follows.
- API tokens for scripts and LLMs: a user signed in with a password makes named tokens (`POST /api/v1/tokens`, body `name` and `scope`), lists their own (`GET /api/v1/tokens`) and revokes them (`DELETE /api/v1/tokens/{id}`). The text of a token (`vxt_…`) is shown once; the server keeps only its digest (migration 6). A token is sent as a bearer token like a login, also on the real-time channel. Its scope is `read_only` (reads library, bookmarks and exports) or `edit_bookmarks` (also edits, replaces and imports bookmarks); what it may do is the cut of that scope and its user's role, so a token never plays, uploads, manages recordings or users, and cannot make tokens. `/api/v1/me` reports the reduced capabilities. A token ends with its revocation, or when its user is deactivated or deleted; a new password does not end it.
- Bookmark import: `POST /api/v1/import` takes the export format as JSON, or a table with the content type `text/csv` (`GET /api/v1/export?format=csv` writes the same columns), and replaces the bookmarks of each recording it names. `?dry_run=true` only reports what would change; the answer lists per recording the status (`ok`, `conflict`, `invalid`, `unknown_recording`), the counts (added, changed, unchanged, removed) and the issues with their place (`labels[2]`). An entry that carries the id and version of a stored bookmark conflicts when that bookmark changed or is gone meanwhile, unless `?overwrite=true`. Recordings are applied one by one; one that is refused stays as it was. `GET /api/v1/import/schema` serves the JSON schema. Reasons: `import_malformed`, `import_format_unsupported`, `csv_invalid` (with the line), `export_format_unknown`.
- The position no longer jumps back after a click or a jump: a seek, restart, play from a label, a region start or the release of the handle shows the asked position at once (moving on with a playing recording) until the server's position has caught up, for 1.5 seconds at most. Before, the old position showed until the server answered, which a slow connection made visible as a step back and forth.
- Livelier player and top bar: panels (tempo, pitch, volume, markers on a wide screen, framed buttons) are filled surfaces with a teal edge and glow instead of bare outlines; the play button glows orange; the connection status is a coloured pill; the selected tab of the top navigation is outlined in orange. The player's head shows an icon tile and a line with key, tempo and length under the title, and a clock "position / length" stands beside the transport.
- The waveform has a stage: a dark, framed band with a zero line, amplitudes drawn bright in the middle and deeper towards the peaks, and the part after the playhead muted so the played part stands out. The playhead glows orange. Regions are filled bars in their tone on faint lane tracks; on a wide screen waveform and transport share one panel.
- Livelier library: recordings are cards, the one whose details are shown is outlined in orange; key, tempo and tuning stand as chips (read out as one line). A pending analysis shows its state with a bar, filled by the reported share while it runs and running indeterminately while it waits; a recording analysed again shows the progress instead of the values about to be replaced. The details are a framed panel with the recording's whole waveform on top, its values as chips, and "Open in the player" as the main action; without a chosen recording the panel says how to get details.
- Empty, loading and error states share one shape (`StateNotice`): an icon badge (a spinner while something is under way), the message and the next action where there is one, on a panel framed in red for an error. Used for the empty library, no search match, loading and failing library, no markers, failing markers, no recording in the player and the check before sign-in; the missing waveform shows the empty stage with an icon. The screens before the app show the full logo (large turtle above the wordmark, the full form of `BrandMark`) and the form on a framed panel over a faint teal glow.
- The client notes why it gives up the real-time channel: a line `veltrunox: channel failed: …` (or `channel closed …`) in the browser console (standard error natively) with the reason, such as a socket error, a message it did not understand, a different protocol version or a playback state with an invalid value. No tokens or user data are written.
- The analysis of a new recording no longer decodes the whole file into memory: decoding, waveform, spectrum and length are built in one pass over the decoded pieces. A long recording used to need hundreds of megabytes at once, enough for the kernel to stop the server on a small Raspberry Pi; the results are the same. Playback still holds the decoded recording that is loaded.
- The server writes a line to standard error when it closes a real-time channel, with the reason: the client was silent for more than 30 seconds, the client closed, the connection failed, or a ping could not be sent.
- Without `--config` the server (and the `users` command) also looks for `/etc/veltrunox/veltrunox.toml`, after `veltrunox.toml` in the working directory. The installer writes `data_dir` as an absolute path (`/var/lib/veltrunox/data`) into a new configuration, so the command line works from any directory.
- User administration on the command line: `veltrunox-server [--config <file>] users <command>` lists, creates (including the first admin), deletes, enables and disables users, sets passwords and roles, switches guest access and the password rules, working directly on the database without the HTTP interface (the server may be stopped). The password is asked for twice without echo, or read from standard input with `--password-stdin`. The rules of the account service apply (name and password rules, the last active admin stays); a new password ends the sessions of that user.
- Upload progress in bytes: an upload may carry an id in the `x-upload-id` header; the server counts the bytes it has received and publishes `upload_progress` events (`upload_id`, `received_bytes`, at most about ten per second) over the real-time channel. The client core passes them on (`SessionUpdate::UploadProgress`; `upload_recording` takes the id), and the library bar shows the percentage of the file that has arrived ("Uploading: song.wav – 42 %"). A malformed id is refused with `upload_id_invalid`; an upload without an id works as before. Files that arrive within a tenth of a second show no percentage.
- Refusals carry a code instead of a sentence: every error body is JSON `{"code", "args", "message"}` (HTTP) and `rejected` on the real-time channel carries the same object; `code` is stable, `args` are the numbers the text needs (a limit, seconds), `message` is English for logs and for codes a client does not know. Failed analyses store and send the code too (`{"state":"failed","code":"analysis_too_short"}`). The client core and the bridge pass the reason on as it is (`ReasonInfo`; upload, rename and delete report `RecordingActionError`), and the interface words it in German or English from a table of codes. Before, the English sentence of the server served as the key of the translation. Failed analyses stored before this change show only "Analysis failed".
- Interface in German and English (D-21): every text comes from a catalogue per feature (`tr(de, en)`), the language follows the browser at the first visit, can be switched in the status area and on the sign-in screens, and is kept on the device. The server's English refusal reasons and analysis failures are shown in German in the German interface and as the server words them (with a full stop) in the English one; numbers use the decimal comma or point of the language. Texts of the browser's own widgets (for example the text field menu) stay in the browser's language.
- Without a connection to the server the player controls are dimmed and cannot be used, and a value that was dragged or typed but not sent is reset to the shared state (D-22); the banner says that nothing is processed.
- When someone else changed a marker first, a write is refused and the notice says so, instead of the general "not applied" message (D-19). The client core reports the conflict to the interface as the reason `conflict`.
- The library lists the length of each recording (protocol: `length_ms` in the recording summary, absent until the scan is done; shown in the details). The player's position slider and waveform no longer wait for the analysis: they appear once the length is known, so a recording whose analysis failed (for example silence) has a slider as well. `recording_length_ms` in the bridge is gone.
- New real-time event `library_changed` for recordings that were added, renamed or removed (upload, rename, delete); `analysis_changed` stays for the status and result of one recording. The library reloads on both.
- The running analysis reports its progress in percent (`{"state":"running","percent":40}`): decoding, waveform and the analysis stages report to the scan, clients are told in steps of 5 percent, and the library shows "Analysing … 40 %".
- Upload of several files: the file dialog takes a selection, the files are sent one after the other (each read only when it is its turn), the bar shows which one is on its way, and a summary tells how many were added, were there already or were refused; a refused file does not stop the rest.
- Small interface fixes: the server's English refusal reasons (sign-in, user administration, upload, rename, rejected commands) are shown in German, unknown ones as the server says them; when the server no longer accepts the sign-in during a session (expired, revoked, guest access switched off), the app returns to the sign-in with a sentence saying so; playing a label or region from the list scrolls the waveform to it; a banner says when the server has no audio device (the bridge passes the notice on as `SessionUpdate::AudioOutput`).
- Password rules are a setting of the admin: `standard` (default, at least 6 characters) or `strict` (at least 10 with a lowercase letter, an uppercase letter, a digit and a special character); the user administration has a switch, the forms for a new user and a new password say what is missing, and the server enforces the rule (`PUT /api/v1/password-policy`, shown in the public status). Existing passwords stay valid. Before, every password needed 10 characters.
- Fix: signing out did nothing in the browser, because closing the real-time session waited for the stream to end; the session is now released without waiting. A regression test signs out in the browser.
- Upload and recording administration in the library: an upload button above the list (for everyone who may upload) opens the system's file dialog, shows that the file is being sent, then that it was added, that the same audio was there already, or why the server refused it. The admin renames a recording from its details and deletes it after a confirmation that names it. Actions a role may not do are not shown.
- Upload and recording administration in the client core and the bridge: `upload_recording` (the file in one request; the server's reason comes back when it refuses a file), `rename_recording_to` and `delete_recording_for_good`.
- Upload and recording administration on the server (ADR-012): `POST /api/v1/recordings` takes an audio file as the raw body (name in the `x-file-name` header, size limit `max_upload_bytes`, default 512 MiB), checks that the decoder can read it, stores it by content hash in `upload_dir` (default `<data_dir>/media`) and queues its analysis; the same audio again returns the existing recording. Users, guests and the admin may upload. The admin renames (`PUT /api/v1/recordings/{id}`) and deletes recordings (`DELETE`: bookmarks, analysis and waveform go too, a loaded recording is unloaded, an uploaded file is removed, files of an imported directory are never touched). At start-up the server removes files in the upload directory that no recording refers to.
- Sign-in in the app: before the app, a screen asks for user name and password (hidden until shown), offers guest access while the server allows it, and on a server without users sets up the first admin (password repeated, at least 10 characters). A sign-in is kept in the browser's local storage and resumed at the next start; an expired one is dropped. The top bar has an account menu (who is signed in, sign out, and for the admin the user administration). The user administration is a dialog, not a place in the navigation: guest access on/off, role, active, new password, delete with confirmation, new user. Failures are explained in a sentence (wrong password, not allowed, too many attempts with the wait, refusal by the server). The real-time session opens only after signing in. The browser tests sign in (and set the admin up on a fresh server).
- Accounts and rights on the server (ADR-012): the first start sets up one admin (`POST /api/v1/setup`, no default password); users sign in with name and password (`/login`, Argon2id hashes, random session tokens stored as digests, 30 days idle expiry, growing delay after failed logins). Roles are admin, user and an optional guest (off by default, switched by the admin); every endpoint and every real-time intent checks the role's rights on the server, and the real-time channel expects `auth` as the first client message. Admin endpoints manage users and the guest switch; the last active admin cannot be removed.
- Sign-in in the client core and the bridge: status, first-admin setup, sign-in with a resumable token, guest access, sign-out, the rights of the signed-in person and user administration; the real-time channel presents the token (or guest access) first and reports the rights. The interface has no sign-in screen yet, so the app still cannot connect to a server that requires sign-in.

- Pausing puts the audio engine on the frozen position, so repeated pauses no longer move the sound ahead of the shared position.

- Release build of the server: settings come from a TOML configuration file (`--config <file>`), which replaces the `VELTRUNOX_*` environment variables (`address`, `data_dir`, `media_dir`, `audio_device`, `allowed_origin`, `web_dir`). The `embedded-web` feature bakes the web app into the binary; `scripts/build-release.sh` builds both, and `dist/install.sh` installs the Pi build as a systemd service. The web app bundles CanvasKit and fonts instead of loading them from Google's CDN (works without internet) and keeps only the CanvasKit variants it uses; the server compresses responses (gzip, Brotli).
- Analysis of tuning, key and tempo (ADR-007): runs in the background after start-up for every recording without a result and can be started again per recording; results are stored with the recording, clients are told when one changes, and the library shows key, tempo and tuning or the state of the analysis.
- Waveform overview and recording length: the background scan decodes each recording once and stores the length and min/max peaks in levels from coarse to fine; `GET /api/v1/recordings/{id}/waveform` describes the levels, `.../waveform/{level}` returns the peaks as bytes. Recordings stored without them are scanned again at start-up. Seeks and loop ends beyond the length are refused, also after a restart.
- The playback pitch uses the analysed tuning of the recording (concert pitch until it exists).
- The player shows the tempo the recording plays at, takes a wanted tempo (speed is derived from it) and sets speed, tuning and key back to the analysed values.
