# Changelog

## Unreleased

- Small interface fixes: the server's English refusal reasons (sign-in, user administration, upload, rename, rejected commands) are shown in German, unknown ones as the server says them; when the server no longer accepts the sign-in during a session (expired, revoked, guest access switched off), the app returns to the sign-in with a sentence saying so; playing a label or region from the list scrolls the waveform to it; a banner says when the server has no audio device (the bridge passes the notice on as `SessionUpdate::AudioOutput`).
- Password rules are a setting of the admin: `standard` (default, at least 6 characters) or `strict` (at least 10 with a lowercase letter, an uppercase letter, a digit and a special character); the user administration has a switch, the forms for a new user and a new password say what is missing, and the server enforces the rule (`PUT /api/v1/password-policy`, shown in the public status). Existing passwords stay valid. Before, every password needed 10 characters.
- Fix: signing out did nothing in the browser, because closing the real-time session waited for the stream to end; the session is now released without waiting. A regression test signs out in the browser.
- Upload and recording administration in the library: an upload button above the list (for everyone who may upload) opens the system's file dialog, shows that the file is being sent (no percentage: a browser reports none), then that it was added, that the same audio was there already, or why the server refused it. The admin renames a recording from its details and deletes it after a confirmation that names it. Actions a role may not do are not shown.
- Upload and recording administration in the client core and the bridge: `upload_recording` (the file in one request; the server's reason comes back when it refuses a file), `rename_recording_to` and `delete_recording_for_good`. No byte progress: a browser reports none for an upload.
- Upload and recording administration on the server (ADR-012): `POST /api/v1/recordings` takes an audio file as the raw body (name in the `x-file-name` header, size limit `max_upload_bytes`, default 512 MiB), checks that the decoder can read it, stores it by content hash in `upload_dir` (default `<data_dir>/media`) and queues its analysis; the same audio again returns the existing recording. Users, guests and the admin may upload. The admin renames (`PUT /api/v1/recordings/{id}`) and deletes recordings (`DELETE`: bookmarks, analysis and waveform go too, a loaded recording is unloaded, an uploaded file is removed, files of an imported directory are never touched). At start-up the server removes files in the upload directory that no recording refers to.
- Sign-in in the app: before the app, a screen asks for user name and password (hidden until shown), offers guest access while the server allows it, and on a server without users sets up the first admin (password repeated, at least 10 characters). A sign-in is kept in the browser's local storage and resumed at the next start; an expired one is dropped. The top bar has an account menu (who is signed in, sign out, and for the admin the user administration). The user administration is a dialog, not a place in the navigation: guest access on/off, role, active, new password, delete with confirmation, new user. Failures are explained in a sentence (wrong password, not allowed, too many attempts with the wait, refusal by the server). The real-time session opens only after signing in. The browser tests sign in (and set the admin up on a fresh server).
- Accounts and rights on the server (ADR-012): the first start sets up one admin (`POST /api/v1/setup`, no default password); users sign in with name and password (`/login`, Argon2id hashes, random session tokens stored as digests, 30 days idle expiry, growing delay after failed logins). Roles are admin, user and an optional guest (off by default, switched by the admin); every endpoint and every real-time intent checks the role's rights on the server, and the real-time channel expects `auth` as the first client message. Admin endpoints manage users and the guest switch; the last active admin cannot be removed.
- Sign-in in the client core and the bridge: status, first-admin setup, sign-in with a resumable token, guest access, sign-out, the rights of the signed-in person and user administration; the real-time channel presents the token (or guest access) first and reports the rights. The interface has no sign-in screen yet, so the app still cannot connect to a server that requires sign-in.
- Turning a label into a region and back is one server call (`POST /api/v1/labels/{id}/to-region`, `POST /api/v1/regions/{id}/to-label`): the old marker is deleted and the new one created in one transaction, so a failure or a stale version leaves the old marker untouched. The marker form uses it.
- The client core forgets a recording's waveform when the server reports a new analysis of it, so a new scan shows up without restarting the app.
- Web icons: the favicon and the app icons use the turtle instead of the Flutter defaults; the manifest and the page title say "Veltrunox" with the dark background colour.
- Architecture: audible scrubbing is documented in ADR-011 and replaces the fallback in ADR-005. The design specification no longer proposes library filters by key or tempo.
- Player on a large screen: the page fits the screen (from 720 px height, with the markers beside) and only the region lanes below the waveform and the marker list scroll, the tempo and pitch panels sit at the bottom, and the waveform takes the height the regions leave, so it is taller with few regions; on a lower screen the whole page scrolls as before. The volume panel ends where the tempo and pitch panels begin, and those reach the right edge; the volume stands beside the transport only from 900 px of controls width.
- Player tweaks: "Set label here" and "Create region here" moved from two buttons below the waveform into the waveform toolbar (icons next to zoom, fit and snap); the region button creates a region at the playhead and replaces drawing a region by dragging. The time above the play button is gone (the playhead shows it). On a wide screen the volume panel reaches down to the bottom of the tempo and pitch panels. Region lanes are laid out anew once a handle is let go, so regions that no longer overlap share a lane again. The zoom never goes below the whole recording, also after the window is resized.
- Waveform and player layout after trying it: a click on the waveform sets the position even if the pointer wobbles slightly; pressing the ruler puts the playhead there and dragging goes on from there; the exact time stands in a chip above the playhead and the ruler; two fingers pinch to zoom and move to pan (they no longer scroll the page), and on a trackpad a sideways swipe pans and a pinch zooms; a click outside the selected region leaves its edit mode. "Set label here" and "Create region here" are two buttons below the waveform (the region runs from the playhead to the end of the visible range and is selected). One form edits and creates markers: Start and an optional End, so a label becomes a region when an end is entered and a region becomes a label when it is cleared (the new marker is added before the old one is deleted). On a wide screen the markers stand on the left and the volume beside the waveform and the transport; on a narrow one the button for the markers sits above the waveform.
- Waveform in the player: a scanned recording shows its waveform in place of the position slider (the slider component stays for simpler views). Tapping a label or region plays it; a tap on the free waveform moves the position without playing; dragging the playhead scrubs with the same hold-to-play-on behaviour as the slider; "Set label here" adds a label at the position; the region button plus a drag adds a region and selects it; dragging a handle of the selected region writes the new times; a long press on a marker offers edit and delete. Markers changed by other clients appear at once. The client core fetches all levels of a recording's waveform once and keeps them in memory (`recording_waveform` in the bridge).
- Waveform components, not yet in the player: ruler, amplitude renderer, playhead with scrubbing, label chips that group when they collide (`+N`), region lanes without overlaps (stable while a handle is dragged; two lanes plus "all regions" on a narrow screen), handles on the selected region, snapping to labels and region ends, tap/pan/pinch/wheel gestures, drawing a region, and zoom, fit and snap buttons. The view (visible range, snap, selection) is local state. Tested with the real peaks of a recording and the design specification's test scene.
- Debug builds optimise their dependencies and the audio crate: decoding a song took about 4 s (0.16 s in a release build), during which the previous song kept playing and the new one started that far into the recording. The other workspace crates stay unoptimised.
- Library and player without the waveform: the library is a large song list with search (title, key, tempo), sorting (title, tempo, key), a filter by analysis state, a play button per recording and the state of its analysis on each row; a recording's details (values, open in player, play, analyse again) stand beside the list from 1024 px and replace it on a narrower screen. The player is its own screen with the recording's title, a play mode toggle next to the play button (to the end, to the region end, loop; shared by all clients), and the marker list: labels and regions in one chronological list with a filter, a play button per row (a label plays on from its position, a region from its start), a region form (name, start, end, checked against the recording's length) that also edits a region, a form to rename or move a label, and deletion after a confirmation naming the marker; on a narrow screen the list opens in a sheet. Empty, loading, error and disconnected states are shown: a banner with a "reconnect" button while the connection is lost, and a short notice when another client moved the position. The bridge reads and writes labels and regions (versioned; a stale version is refused).
- App foundations: design tokens as Dart constants (from `design-tokens.json`), a dark theme with a visible focus ring and 48 px touch targets, shared components (`ActionButton`, `AppIconButton`, `ToastNotice`, `ConfirmDialog`, `ActivityStatus`) and an app shell with navigation Player / Library (bottom bar on mobile, side rail on tablet, top bar from 1024 px) and the connection status always visible. Library and player use the theme; the play button is the large primary control, a pending or failed analysis shows an icon with its text, and the connection status shows an icon too. Inter is bundled. The logo (turtle and wordmark) sits in the shell's title bar, the selected navigation entry is orange in every layout, and the position slider is always shown (disabled until the recording's length is known). The title bar is black with the logo (turtle and wordmark) at every width, and tempo (metronome), pitch (tuning fork) and volume are panels. Tempo shows the analysed tempo; pitch takes a tuning in Hz and a key chosen from a dropdown of -12 to +12 semitones, named after the analysed key; tempo and tuning each have one field that shows the value (tuning with one decimal) and takes a new one (the wanted tempo is disabled without an analysis), the sliders show no label, the transport symbols are larger, the panels and the back-to-start button are transparent with a border and a faint glow on the one dark background, and the reset buttons are always shown (dimmed when there is nothing to reset). Key names use `#` because the font has no sharp sign. From 1000 px the panels stand side by side and the volume slider stands upright beside the transport. Sliders have a cyan track and a white handle. On a small screen the player scrolls instead of overflowing.
- Region playback (ADR-010): the shared state holds a play range and a play mode (to the end of the recording, to the end of the region, looped) instead of a loop range; `play_region` starts a region in one step and `set_play_mode` changes the mode, replacing `set_loop`. Playback to the region end stops in the audio engine at that sample with a short fade, and the server pauses at the computed instant (not by polling). The bridge exposes the range, the mode and both commands to the app.
- Holding the position handle still for a moment lets the recording play on from there; moving it again scrubs again. A stopped recording plays only while the handle is held and stops again when it is let go.
- Audible scrubbing: dragging the position handle plays a short piece (120 ms, as recorded, with short fades) at each position instead of staying silent, and the shared position holds under the handle while it is dragged, then runs on from where it is let go.
- Design specification v0.1 and design tokens (`docs/design/`): player, waveform with labels and region lanes, library, states, accessibility and UI acceptance criteria.
- Player: a position slider with scrubbing (the length comes from the stored scan; the slider appears once a recording is analysed); the speed slider takes effect while it is dragged and shows the wanted tempo under the handle; the tuning slider is replaced by a field for the wanted tuning in Hz (300–500, with a message otherwise) that sets it back to the analysed value. Loops and regions are not part of this.
- Output volume (ADR-009): a slider in the player sets the volume of the server for everyone, and every client shows the current value. The server sets the sound card's mixer where there is one (ALSA, for example the Pi's headphone output) and scales the audio itself otherwise; at start-up it reads the mixer.
- Pausing puts the audio engine on the frozen position, so repeated pauses no longer move the sound ahead of the shared position.
- The position display reads the position when the displayed tenth changes while playing, so the tenths advance evenly.
- Release build of the server: settings come from a TOML configuration file (`--config <file>`), which replaces the `VELTRUNOX_*` environment variables (`address`, `data_dir`, `media_dir`, `audio_device`, `allowed_origin`, `web_dir`). The `embedded-web` feature bakes the web app into the binary; `scripts/build-release.sh` builds both, and `dist/install.sh` installs the Pi build as a systemd service. The web app bundles CanvasKit and fonts instead of loading them from Google's CDN (works without internet) and keeps only the CanvasKit variants it uses; the server compresses responses (gzip, Brotli).
- Analysis of tuning, key and tempo (ADR-007): runs in the background after start-up for every recording without a result and can be started again per recording; results are stored with the recording, clients are told when one changes, and the library shows key, tempo and tuning or the state of the analysis.
- Waveform overview and recording length: the background scan decodes each recording once and stores the length and min/max peaks in levels from coarse to fine; `GET /api/v1/recordings/{id}/waveform` describes the levels, `.../waveform/{level}` returns the peaks as bytes. Recordings stored without them are scanned again at start-up. Seeks and loop ends beyond the length are refused, also after a restart.
- The playback pitch uses the analysed tuning of the recording (concert pitch until it exists).
- The player shows the tempo the recording plays at, takes a wanted tempo (speed is derived from it) and sets speed, tuning and key back to the analysed values.

- Project set up: architecture, ADRs (technology stack, GUI architecture, server-side audio output), Clean Code and GUI architecture guidelines, logo.
- Rust workspace with core, protocol, server and client crates; server lists recordings over HTTP, client core fetches them; CI with format, lint, tests and a `wasm32` build check.
- Flutter web app (`app/`) with a library feature that lists recordings through the Rust client core (`flutter_rust_bridge`).
- Real-time channel (WebSocket) with a server greeting; the client core turns link events into connection status with `rxrust`; the web app shows it.
- `scripts/build-web.sh` builds the client core for the browser and the Flutter web app; CI builds it and checks the generated bridge code.

- Automated browser test (Playwright) for the web app; CI caches the build tools.
- Domain model: recordings with playback settings, labels and regions with record versions, the shared playback state and the pure transport operations (select, play, pause, seek, speed, tuning, key, loop).
- Real-time protocol (ADR-005): complete playback state with revision on every change, client intents, clock ping, rejections and bookmark change notices; the server validates every value at the boundary.
- SQLite persistence (ADR-004): recordings, playback settings and bookmarks survive restarts; data directory via `VELTRUNOX_DATA_DIR`. The sample recordings are only added to an empty library.
- Bookmark endpoints with version checks (409 on conflict); client core with session view, clock offset estimate and throttled scrubbing.
- Flutter player bar: select a recording, play/pause, restart, speed, tuning and key, shared live between clients; the bridge exposes the session (`watch_session`, `send_command`, `playback_position_ms`). Browser test with two clients.
- Client core reconnects on its own with doubling, capped delays and measures the clock offset on connecting and every minute; the generated bridge no longer exposes a separate clock call.
- Browser test for reconnection: the web app shows "Getrennt" when the server stops and "Verbunden" again after it restarts (`e2e/playwright.reconnect.config.ts`).
- ADR-006: audio pipeline with `symphonia`, `cpal` and `signalsmith-stretch`.
- Playback on the server: audio files are decoded (`symphonia`), stretched and pitch-shifted (`signalsmith-stretch`) and played through the audio device (`cpal`); speed, tuning, key, loop and scrubbing follow the shared state. `VELTRUNOX_MEDIA_DIR` imports audio files as recordings (duplicates by content hash), `VELTRUNOX_AUDIO_DEVICE` picks the device.
- Target tempo to speed (with out-of-range hint) and tuning/key to pitch shift as pure operations.
- `scripts/build-pi.sh` cross-builds the server for a 64-bit Raspberry Pi.
- Playback pauses at the end of the recording; a seek beyond the end is rejected once the length is known; clients are told over the channel whether the server has an audio output.
- The server serves the built web app itself when `VELTRUNOX_WEB_DIR` is set.
- The web app talks to the origin it was loaded from, so the server's address and port are set with `VELTRUNOX_ADDRESS` without rebuilding; browser tests run against the server-hosted app.
